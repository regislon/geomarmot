# 0011 — Rust rewrite: feasibility spike outcome

**Status:** proposed — spike outcome **go, pending one CI run**: every gate passes on macOS and in
Chromium; the same checks on Linux and Windows are written and wait for their first CI run.
Decided by the owner.

## Context

[docs/rust-migration-plan.md](../rust-migration-plan.md) (revision 7) asks for a fixed-scope spike
before the rewrite: seven gates, with go, no-go or inconclusive as outcomes. The code is in
[`rust/`](../../rust/README.md), on the `rust-spike` branch. All timings are on the reference
machine (Apple M2 Pro, 12 cores, 32 GB, macOS 26.2), release builds.

## Evidence per gate

**1. Fixtures — pass on all three engines.** A Rust port of the fixture harness
(`geomarmot-conformance`: run-case, compare, WKT, exact and topology modes) runs the 37 cases of
AttributeFilter, FeatureJoiner, Dissolver, Reprojector, Bufferer (both per-feature projections),
AreaOnAreaOverlayer, MinimumBoundingCircle (a per-feature kernel, `geo`) and H3GeometryFromIndex
(`h3o`): **37/37 in-process, 37/37 through the engine process, 37/37 on DuckDB-Wasm in Chromium**
(`rust/web/gate1.spec.js`). The Rust comparator is cross-checked against
`tests/harness/compare.js`: every port the fixtures produce, as produced and broken three ways
(a row missing, a geometry moved by 1e-3, a value changed), 152 verdicts, 110 rejections, no
disagreement (`rust/crates/conformance/crosscheck.mjs`).

**2. Overlay — pass; GEOS chosen.** The GEOS core (clustering, noding, polygonize, certified
interior points, containment) is ported to Rust and runs in parallel inside the engine. It passes
`tests/fixtures/geos-overlay-parity.json` and the 11 overlay fixtures natively. In the browser the
app's existing GEOS worker pool is the kernel, through the bridge; the 11 fixtures pass there too.
A pure-Rust core on `geo` **fails**: its boolean operations snap to a grid, so faces drift by about
1e-8 (limit 1e-12), sliver faces appear and adjacent faces merge (the donut case gives 6 faces, not
8). GEOS stays the overlay kernel on both targets. The constrained-Delaunay incentre step is skipped
in the Rust port (not wrapped by the `geos` crate); it changes cost, not results.

**3. Readers — pass, with a design change.**

| Measure | Result |
|---|---|
| 200,000-polygon GeoPackage to a DuckDB table | DuckDB `ST_Read` 53 ms, terrio 285 ms (median of 5); same rows and geometry |
| Parquet over HTTP range reads, 150 MB file | `count(*)` fetched 0.26–0.5 MB; one filtered column 0.4–0.9 MB |
| GeoPackage written by terrio, read back by terrio and by `ST_Read` | same rows and geometry |

Finding: on DuckDB 1.5.4, GDAL inside a locked engine probes sidecar files (`name.*`,
`name.gpkg-journal`, `name.gpkg.aux.xml`) that the exact-path allow list refuses. GeoPackage,
GeoJSON and FlatGeobuf are therefore imported by terrio inside the engine process, under the same
allow list (`io::authorize`), and DuckDB never opens them. This is slower than `ST_Read` (5.4× on the
GeoPackage above) but keeps the file-system boundary exact, and it is the reader the owner asked
for. Parquet and CSV stay on DuckDB's lazy readers. terrio widens `INTEGER` to `BIGINT` and drops a
layer's CRS on write unless told; both are follow-ups for the I/O phase.

**4. Cancellation and responsiveness — pass.**

| Case | Desktop (engine process) | Browser (DuckDB-Wasm) |
|---|---|---|
| Long scan, cooperative | stopped in 12 ms | stopped in 37–87 ms |
| Nested-loop join, cooperative | stopped in 12 ms | stopped in 34 ms |
| Single operation that cannot yield | killed at 2 s, new engine in 2.08 s total | killed at 2 s, new engine in 4.2 s total |
| Approve a new source (restart + register) | ~50 ms | n/a (no restart needed) |
| Kill during an export | destination untouched, staging cleaned | n/a |
| Kill a preview engine | main engine untouched | n/a |

Requests carry the engine epoch; replies from an older one are dropped. An interrupt also cancels
requests still queued. In the browser, statements stream (`send`), because `cancelSent` cannot reach
a blocking `query`. Frame times with the engine busy for 10 s:

| | Start to first frame | p50 | p95 | p99 | Longest |
|---|---|---|---|---|---|
| Desktop (`GEOMARMOT_PROBE=1`, 5 runs) | 186–236 ms (median 195) | 8.3 ms | 13.3–16.7 ms | 14.8–18.2 ms | 56–67 ms; 105.5 ms on the first run |
| Browser (Playwright, Chromium) | ~1.0 s with DuckDB booted | 16.7 ms | 16.8 ms | 16.8 ms | 16.8 ms |

The desktop's longest frame passed the 100 ms stall budget once in five runs (the first, cold);
p95 and p99 are well within budget.

**5. One usable flow — pass on both targets.** Desktop: a headless egui test drives the real window
through Reader → Bufferer → Dissolver, reads the table, exports Parquet through staging, and renders
screenshots. Browser: the same app code built to wasm; checked by hand in Chromium (open, add and
wire a transformer, table, map) and by a Playwright spec through small wasm test hooks (open a file,
chain Bufferer and Dissolver, read the table, export a download). Keyboard navigation beyond the
inspector's text field is not tested; it belongs to the UI phase's accessibility checks.

**6. Security and lifecycle — pass on both targets.** Engines boot locked: bundled extensions only,
`enable_external_access = false`, exact `allowed_paths` (native) or the page's own `/gm/` directory
(browser), `lock_configuration`. Every row of the plan's security table holds on both native engines
and on DuckDB-Wasm with the guard bypassed; the ported SQL guard refuses every row and passes the
browser suite's cases. `allowed_paths` cannot be extended once access is off, so approving a source
restarts the native engine (~50 ms). terrio imports obey the same allow list, and a test fails if
engine code touches the file system outside `io.rs`. DuckDB's `arrow()` table function is not used:
it takes raw pointers from SQL. Retiring a generation drops all its views and `prepare` tables and
leaves the next one untouched. In the browser, `INSTALL` is accepted by DuckDB-Wasm, but nothing
unbundled loads.

**7. Runtime check per target — macOS passes; Linux and Windows written, not run.** On macOS
arm64 a locked engine loads the bundled extensions and answers a spatial query and a Parquet read.
`.github/workflows/rust-spike.yml` runs the same on Linux (network off) and Windows, the native
gates on all three, and the browser specs in Chromium; it runs on the first pull request that
touches `rust/`.

## Outcome

**Go**, once `rust-spike.yml` has run green on Linux and Windows. Every gate passes on macOS and in
Chromium, and no finding changes the plan's architecture. The one budget miss (a single 105.5 ms
frame on a cold desktop start, against 100 ms) is noted, not blocking.

Carried into the phases, not blocking: per-feature kernels run on the browser's main thread (a
kernel worker is still to build); integer H3 indexes; one source per GeoPackage layer; terrio's type
widening and CRS on write; a basemap; keyboard navigation and assistive-technology checks.

## Consequences

- The engine split is confirmed: DuckDB native and DuckDB-Wasm on one 1.5.4 core, Rust kernels
  beside them, Arrow between them.
- GEOS is the overlay kernel everywhere; the pure-Rust `geo` overlay is not an option.
- Vector formats are read by terrio, not by GDAL, while the engine is locked to exact paths.
- Safety caps (`MAX_OVERLAY_FEATURES`, `MAX_MATERIALISED_CELLS`) are unchanged until the
  performance checkpoint.
