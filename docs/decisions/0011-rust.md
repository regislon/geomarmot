# 0011 — Rust rewrite: feasibility spike outcome

**Status:** proposed — spike outcome **inconclusive, leaning go**: every central risk is retired, a
bounded list of checks is still open (below). Decided by the owner.

## Context

[docs/rust-migration-plan.md](../rust-migration-plan.md) (revision 7) asks for a fixed-scope spike
before the rewrite: seven gates, with go, no-go or inconclusive as outcomes. The code is in
[`rust/`](../../rust/README.md), on the `rust-spike` branch. All timings are on the reference
machine (Apple M2 Pro, 12 cores, 32 GB, macOS 26.2), release builds.

## Evidence per gate

**1. Fixtures — pass on all three engines, two items open.** A Rust port of the fixture harness
(`geomarmot-conformance`: run-case, compare, WKT, with exact and topology modes) runs the 33 cases of
AttributeFilter, FeatureJoiner, Dissolver, Reprojector, Bufferer (both per-feature projections) and
AreaOnAreaOverlayer: **33/33 in-process, 33/33 through the engine process, 33/33 on DuckDB-Wasm in
Chromium** (`rust/web/gate1.spec.js`). Open: the Rust comparator is checked by its own self-test,
not yet cross-checked against `tests/harness/compare.js`; no H3 case and no per-feature JSTS-style
kernel case was ported.

**2. Overlay — pass; GEOS chosen.** The GEOS core (clustering, noding, polygonize, certified
interior points, containment) is ported to Rust and runs in parallel inside the engine. It passes
`tests/fixtures/geos-overlay-parity.json` and the 11 overlay fixtures natively. In the browser the
app's existing GEOS worker pool is the kernel, through the bridge; the 11 fixtures pass there too.
A pure-Rust core on `geo` **fails**: its boolean operations snap to a grid, so faces drift by about
1e-8 (limit 1e-12), sliver faces appear and adjacent faces merge (the donut case gives 6 faces, not
8). GEOS stays the overlay kernel on both targets. The constrained-Delaunay incentre step is skipped
in the Rust port (not wrapped by the `geos` crate); it changes cost, not results.

**3. Readers — pass, with a design change.**

| Measure | Result |
|---|---|
| 200,000-polygon GeoPackage to a DuckDB table | DuckDB `ST_Read` 53 ms, terrio 285 ms (median of 5); same rows and geometry |
| Parquet over HTTP range reads, 150 MB file | `count(*)` fetched 0.26–0.5 MB; one filtered column 0.4–0.9 MB |
| GeoPackage written by terrio, read back by terrio and by `ST_Read` | same rows and geometry |

Finding: on DuckDB 1.5.4, GDAL inside a locked engine probes sidecar files (`name.*`,
`name.gpkg-journal`, `name.gpkg.aux.xml`) that the exact-path allow list refuses. Naming the file in
`sibling_files` silences the first probe, not the others. GeoPackage, GeoJSON and FlatGeobuf are
therefore imported by terrio inside the engine process, under the same allow list (`io::authorize`),
and DuckDB never opens them. This is slower than `ST_Read` (5.4× on the GeoPackage above) but keeps
the file-system boundary exact, and it is the reader the owner asked for. Parquet and CSV stay on
DuckDB's lazy readers. terrio widens `INTEGER` to `BIGINT` and drops a layer's CRS on write unless
told; both are follow-ups for the I/O phase.

**4. Cancellation and responsiveness — cancellation passes; responsiveness not measured.**

| Case | Desktop (engine process) | Browser (DuckDB-Wasm) |
|---|---|---|
| Long scan, cooperative | stopped in 12 ms | stopped in 37 ms |
| Nested-loop join, cooperative | stopped in 12 ms | stopped in 34 ms |
| Single operation that cannot yield | killed at 2 s, new engine in 2.08 s total, usable at once | killed at 2 s, new engine in 4.2 s total |
| Approve a new source (restart + register) | ~50 ms | n/a |
| Kill during an export | destination untouched, staging cleaned | not tested |
| Kill a preview engine | main engine untouched | not tested |

Requests carry the engine epoch; replies from an older one are dropped. An interrupt also cancels
requests still queued. In the browser, statements stream (`send`), because `cancelSent` cannot reach
a blocking `query`; this is what made cooperative cancel work. Open: frame-time budgets (p95/p99,
longest stall) and desktop start time are not measured; kills during import and during a compile
are not tested separately.

**5. One usable flow — pass on both targets; accessibility open.** Desktop: a headless egui test
drives the real window through Reader → Bufferer → Dissolver, reads the table, exports Parquet
through staging, and renders screenshots. Browser: the same app code built to wasm, checked by hand
in Chromium (open, add and wire a transformer, table, map). Open: an automated Chromium test of the
app (only the fixtures page is automated), browser export after the Parquet fix, keyboard
navigation.

**6. Security and lifecycle — pass natively; browser layer and lifecycle test open.** Engines boot
locked: bundled extensions only, `enable_external_access = false`, exact `allowed_paths`, the
staging directory, `lock_configuration`. Every row of the plan's security table holds on both native
engines, with the guard bypassed; the ported SQL guard refuses every row and passes the browser
suite's cases. `allowed_paths` cannot be extended once access is off, so approving a source restarts
the engine (measured above). terrio imports obey the same allow list, and a test fails if engine
code touches the file system outside `io.rs`. DuckDB's `arrow()` table function is not used: it
takes raw pointers from SQL. Open: the browser engine is not locked yet; no test counts relations
before and after a generation is retired.

**7. Runtime check per target — macOS passes; Linux and Windows written, not run.** On macOS
arm64 a locked engine loads the bundled extensions and answers a spatial query and a Parquet read.
`.github/workflows/rust-spike.yml` runs the same on Linux (network off) and Windows, and the
browser fixtures in Chromium; it runs on the first pull request that touches `rust/`.

## Outcome

By the plan's rule ("go: all seven gates pass") this is **inconclusive**: gates 2, 3 and 7 (on the
platform run) pass, gates 1, 4, 5 and 6 pass on their central question with checks still open.
None of the open items is expected to change the architecture. Bounded follow-up, about one week:

1. Run `rust-spike.yml` on Linux and Windows.
2. Cross-check the Rust comparator against `tests/harness/compare.js` on recorded outputs.
3. Port one H3 transformer and one JSTS-style kernel transformer, fixtures first.
4. Measure desktop start and UI frame times under a 10 s kernel workload.
5. Lock the browser engine (URL allow list) and test the security rows there.
6. Count relations and tasks before and after a generation is retired.
7. Automate the browser app flow in Playwright, export included.

**Decision question for the owner:** accept the follow-up list as the remaining spike work and then
start Phase 1, or treat the evidence as sufficient and start Phase 1 now, folding the list into it.

## Consequences

- The engine split is confirmed: DuckDB native and DuckDB-Wasm on one 1.5.4 core, Rust kernels
  beside them, Arrow between them.
- GEOS is the overlay kernel everywhere; the pure-Rust `geo` overlay is not an option.
- Vector formats are read by terrio, not by GDAL, while the engine is locked to exact paths.
- Safety caps (`MAX_OVERLAY_FEATURES`, `MAX_MATERIALISED_CELLS`) are unchanged until the
  performance checkpoint.
