# Rust migration plan

Status: **revision 7, frozen for the spike** (2026-11-09). Further changes come from the spike's
evidence, not from new architecture. The rewrite is decided only after the spike's written
outcome (`docs/decisions/0011-rust.md`). A fixture-only go authorises the port up to the
performance checkpoint; it does not establish large-data speed or authorise removing safety caps.
The full UI is built only after the checkpoint passes.

## Decisions taken (owner, 2026-11-09)

| Question | Answer |
|---|---|
| What "quick" means | **Fastest at runtime.** Processing speed on large data comes before time to ship. |
| UI | **Rewrite in Rust, with egui** (as RustGIS): one UI codebase for desktop and browser. MapLibre is replaced. |
| Engine | **DuckDB native on the desktop, DuckDB-Wasm in the browser**, used where it is the fastest tool; Rust kernels where it is not. Which work goes where is decided by measurement (below). |
| Desktop engine isolation | **A separate engine process.** DuckDB and the kernels run in a child process the app can kill and restart, as the browser does with its worker today. |
| First release scope | **Today's features only.** The formats, transformers and options in [formats.md](formats.md) and the transformer catalogue; new formats are listed separately (below). |
| Browser | **Full feature parity** with today's browser app. Speed parity is not required. |
| Browser parallelism | **One kernel worker is acceptable.** Browser overlays may be slower than today's four-worker overlay; recorded as a deliberate difference in [parity.md](parity.md). |
| terrio | Used for today's formats where it is faster than DuckDB's reader or where DuckDB cannot do the job; the spike measures it. |
| API keys on desktop | **OS keychain** (`keyring` crate). This changes a rule in [AGENTS.md](../AGENTS.md); the change lands with the assistant port, with a test that keys never reach graphs, exports, URLs or logs. |
| Reference hardware | **The owner's machine**: Apple M2 Pro, 12 cores, 32 GB RAM, macOS 26.2. All timings are taken there. |
| Test data | **Fixtures and generated workloads.** No external datasets and no saved-graph corpus for now; tests use `transformers/*/tests.json`, the files `tests/fixtures/build.js` generates, and workloads generated by a script at test time (never committed). |
| Unrestricted SQL | **Kept**, for parity. On the native engine it lifts the SQL guard but not DuckDB's locked configuration (see Security). Assistant SQL stays restricted. |
| DuckDB configuration | **Locked after boot**; approving a new source restarts the engine with the extended allow list; exports go through the staging directory without a restart. |

Revision 2 compared three options (native DuckDB behind the current UI, a Rust engine behind the
current UI, a full rewrite). The owner chose a full Rust rewrite **that keeps DuckDB as the engine**.
That avoids a SQL-engine replacement: DuckDB spatial already supplies the required spatial
functions. Native/browser version differences and saved-SQL compatibility still need validation.

## The engine: who does what, and why

The performance goals are to minimise data copies, use available cores, and bound memory.
Each is measured end to end; choosing Rust or Arrow does not establish any of them by itself.

**Arrow is the intended tabular exchange format.** Pin compatible Arrow versions across
`duckdb-rs`, terrio and the Rust kernels; define the geometry extension metadata, WKB encoding,
CRS, nulls and supported dimensions at the boundary. DuckDB spatial geometry may need conversion
to and from WKB. The browser bridge may serialise Arrow IPC and copy across JavaScript and Wasm
heaps; worker transfers and GEOS bindings also need measurement. Record conversion time, bytes
copied and peak memory. Remove hex-WKB paths only after a tested binary replacement exists.

| Work | Done by | Why |
|---|---|---|
| Filters, joins, aggregates, sorts, attribute work, SQLTransformer | **DuckDB** | Native vectorised execution with parallelism and spilling for eligible operators. Baseline to beat; alternative kernels require measured benefit. |
| Per-row spatial SQL DuckDB has (`ST_Buffer`, `ST_Transform`, `ST_Area`, `ST_Union_Agg` …) | **DuckDB spatial** | Preserve SQL semantics; verify parallelism and performance for the pinned extension. |
| Overlay (AreaOnAreaOverlayer) | **Rust kernel**: GEOS native or `geo` | Not a SQL shape. Desktop: parallel over envelope clusters with `rayon`. Browser: one kernel worker. |
| Minimum bounding box/circle, densify, smooth (today JSTS) | **Rust kernel** on `geo` | Per feature, embarrassingly parallel with `rayon` on the desktop. |
| H3 (cells, polygon fill, positional index) | **Rust kernel** on `h3o`, or the DuckDB `h3` extension if it is faster | Provisional until measured on both targets; extension availability must be proved. |
| Parquet, CSV | **DuckDB's readers** | Retain lazy scans and range reads; measure throughput and bytes fetched. |
| GeoPackage, GeoJSON, FlatGeobuf, Excel, Zarr | **terrio → Arrow → DuckDB**, or DuckDB's `ST_Read` if it is faster | terrio is pure Rust and needs no GDAL; the spike benchmarks both on the same files. |
| Writers (Parquet, GeoParquet, GeoJSON, GeoPackage, CSV, Excel) | DuckDB `COPY` for Parquet/GeoParquet/CSV; terrio for GeoPackage, GeoJSON, Excel | Replace the existing writer only after type, CRS and round-trip parity passes on both targets. |

**After the first release** (not in scope until today's features pass parity): Shapefile,
GeoTIFF/COG, FlatGeobuf writing, other formats terrio offers. Each is added later with its own
fixtures and a [formats.md](formats.md) row.

**How a Rust kernel plugs into the graph.** The compiler still produces one DuckDB view per port,
so SQL outputs remain lazy. Kernel `prepare` steps materialise during compilation, as today: each
streams its input out of DuckDB as Arrow batches, processes them, and registers the result back as
a table through the engine host. Downstream SQL sees an ordinary relation. Batches are bounded
(about 4 MB, as today's overlay batches) with one batch in flight per direction; results are owned
by the generation that produced them. An in-memory overlay or H3 kernel cannot spill because
DuckDB can: kernels keep today's caps and fail cleanly at the memory budget. Measure compile-time
work separately from query time.

## Native engine host

One library, `geomarmot-engine`, holds DuckDB, the bundled extensions, the kernels, the I/O
authorisation (Security, below) and the source recovery records. It has two entry points:

- **In-process**, used by `geomarmot-cli` (Ctrl-C ends the process; nothing to restart).
- **The `geomarmot-engine` binary**, which serves the same host over IPC (Arrow IPC over a local
  pipe), used by the desktop app.

The compiler talks to an engine through one `Engine` trait with three implementations: the
in-process host, the IPC client for an engine process, and the DuckDB-Wasm bridge. All three run
the same fixture suite. The interface is asynchronous (queries return Arrow batch streams) and
covers errors, cancellation, source registration and cleanup; it is defined in the spike.

### Desktop: one app process, two engine processes

```
                                       Arrow IPC  ┌── main engine process ───────────────────┐
 ┌──────── app process (geomarmot) ───────┐ ◀───▶ │ geomarmot-engine: DuckDB, extensions,    │
 │ egui UI · graph model · compiler       │       │ kernels (rayon), approved I/O, staging   │
 │ SQL guard · assistant · keychain       │       └──────────────────────────────────────────┘
 │ approvals (file dialogs, typed URLs)   │       ┌── preview engine process (on demand) ────┐
 │ supervisor: start, watch, kill,        │ ◀───▶ │ geomarmot-engine: 512 MB memory limit,   │
 │ restart, recover                       │       │ no approved paths, sampled inputs only   │
 └────────────────────────────────────────┘       └──────────────────────────────────────────┘
```

- The heavy work and the data stay in the engine process. The app receives only what it shows:
  table pages, map features for the visible extent, port counts, errors.
- **Assistant previews** get their own engine process, started on demand, with a 512 MB DuckDB
  memory limit and a 10 s timeout (as today's isolated engine). It receives sampled copies (at most
  1,000 rows per input) as Arrow from the app, has no approved paths, and is killed on timeout or
  cancel without touching the main engine.
- The supervisor owns cancellation, restart and recovery (below).

### Browser: four threads

```
 ┌──── main thread ─────────────┐  postMessage + transferable ArrayBuffers (Arrow IPC)
 │ app.wasm: egui UI, compiler, │◀──────────────┬───────────────────────────────┐
 │ SQL guard, assistant         │               │                               │
 └──────────────────────────────┘               ▼                               ▼
                        ┌──── DuckDB worker ────────────┐      ┌──── kernel worker ─────────────┐
                        │ DuckDB-Wasm + bundled         │      │ kernels.wasm (geo, h3o;        │
                        │ extensions; sources, views    │◀────▶│ geos-wasm if GEOS is chosen)   │
                        └───────────────────────────────┘      └────────────────────────────────┘
                        ┌──── preview worker (on demand): DuckDB-Wasm, 512 MB, sampled inputs; ─┐
                        │ kernel calls run in a second kernel worker started and killed with it │
                        └───────────────────────────────────────────────────────────────────────┘
```

- Heaps: the app's, DuckDB's, the kernel worker's, and while a preview runs, the preview's. Each
  adds what it holds while working; a batch exists in the sender until it is transferred, then in
  the receiver's heap once copied in. Peak total memory (sum of the heaps) is measured, not assumed.
- Batches cross workers as transferable `ArrayBuffer`s (no structured-clone copy); one batch in
  flight per direction, about 4 MB each, so a slow consumer stops the producer.
- Kernel results go from the kernel worker to the DuckDB worker directly through a
  `MessageChannel`, not via the main thread.
- One main kernel worker (owner decision). Terminating it stops any kernel, even inside one long
  synchronous operation; the next kernel call starts a fresh one.

| | Desktop | Browser |
|---|---|---|
| DuckDB | `duckdb-rs` with `bundled`, in the engine process; extensions (spatial, parquet, json, h3 if used) shipped inside the app, per platform | DuckDB-Wasm in a Web Worker, called through a small `wasm-bindgen` bridge |
| Memory | explicit memory and temp-disk budgets; eligible DuckDB operators spill; kernels may still exhaust memory and fail cleanly | 4 GB per heap, no spilling (unchanged) |
| Kernels | native, all cores (`rayon`), in the engine process | one kernel worker, one thread |
| Previews | separate engine process | separate DuckDB worker and kernel worker |
| Role | the fast path | full features, smaller data |

The bridge and its bundled JavaScript are maintained production code, with contract tests; this
architecture is not Rust-only.

**Version drift.** DuckDB-Wasm lags native DuckDB (the app has DuckDB-Wasm 1.29.0 = DuckDB 1.1.1).
Both are pinned, and CI runs every fixture on both engines. This detects differences covered by
the fixtures; add regression cases for each discovered incompatibility and test saved SQL separately.

## Cancellation

Three separate limits, measured separately, on both targets:

| Step | Limit | Desktop | Browser |
|---|---|---|---|
| **Acknowledge** — the UI shows "Cancelling" and stops accepting results from the cancelled work | 100 ms | app process, no engine round trip | main thread |
| **Stop** — cooperative cancel | 2 s (as ADR 0004) | `Connection::interrupt()` for DuckDB; kernels check a cancel flag between features and between batches | `cancelSent()` for DuckDB-Wasm; kernel flag as on desktop |
| **Escalate** — work still running after 2 s | immediately | the supervisor kills the engine process | the worker that did not stop is terminated |
| **Usable again** — fresh engine, sources recovered, graph recompiled, UI interactive | 5 s on the spike's fixtures; scales with source registration time, recorded per source | new engine process | new DuckDB worker and/or kernel worker |

Cooperative stop is expected to be well under 2 s for scans, aggregates and kernels; nested-loop
joins and a single long geometry operation are known not to stop, which is why escalation exists.

**Identifying results.** Every request carries `(engine epoch, generation id, request id)`. The
epoch increases on every engine start; the app drops any result whose epoch is not the current one,
whose generation has been superseded, or whose request was cancelled.

## Restart recovery

Restarts happen after escalation, after a crash, and when a new source is approved (Security, step
5). Recovery works from **source records** kept by the app (not the engine), one per source:

| Source kind | Record | Recovery |
|---|---|---|
| Local file | approved path; size and modification time at load | re-register the path; if size or mtime changed, the source is marked **changed since loaded** and its downstream nodes say so; the user reloads it explicitly |
| URL, `gs://` | URL; `ETag` / `Last-Modified` at load; credential reference (never the secret) | re-register; changed validators → **changed since loaded**; expired or missing credentials → **needs sign-in**, downstream nodes blocked, no crash |
| Imported snapshot (Excel sheet, Zarr window, inflated `.gz`) | the import's parameters, and a Parquet snapshot written to the staging directory at import | re-register the snapshot; the original file is not read again |
| Dropped file (browser) | the `File` handle, as today | re-read from the handle |

Then the graph is recompiled; `prepare` tables are rebuilt.

**Exports are staged.** DuckDB and terrio write into the engine's staging directory; when the
write completes, trusted I/O copies the file next to the destination as `<name>.partial` and renames
it into place. A kill at any point leaves the destination untouched; staging files and `.partial`
files from an earlier epoch are deleted at the next start.

**Tested** by killing the engine during: an import (Excel, Zarr), a compile with a running kernel,
an assistant preview, and an export. After each, the app is usable within the limit above, results
match a clean run, and no partial file exists at the destination.

## Security

### Unrestricted SQL mode is kept

Today a node's SQL can be switched to **unrestricted** in the inspector, with a confirmation; a
graph opened from a file comes back restricted, and the assistant cannot set the mode
([security.md](security.md)). For full parity this stays, with one redefinition for the native
engine: **unrestricted lifts the SQL guard, not DuckDB's own restrictions.** An unrestricted
fragment may use any SQL DuckDB accepts, but cannot change settings, load extensions or reach files
and URLs outside the approved list, because the configuration below is locked. Assistant-written
SQL and generated transformers stay restricted, with no unrestricted toggle, as today.

### Two layers, each specified

**Layer 1: the SQL guard** (DuckDB's own parser, `json_serialize_sql`, as today) applies to
restricted SQL: user fragments, assistant fragments, generated transformer templates, and saved
graphs opened from a file. It admits one SELECT that reads only the node's inputs, calls no table
function, and uses no function on the deny-list.

**Layer 2: DuckDB's configuration** applies to every statement, restricted or not. Configuration
strategy: **locked**.

1. **Boot.** Load the bundled extensions from the app's own extension directory. Set
   `autoinstall_known_extensions = false`, `autoload_known_extensions = false`,
   `allow_unsigned_extensions = false` (a startup option), the memory limit and the temp
   directory.
2. **Close the file system.** `enable_external_access = false`; `allowed_paths` lists exactly the
   approved source files and URLs (never directories); `allowed_directories` lists only the
   engine's temp and staging directories.
3. **Lock.** `lock_configuration = true`. From here no statement can change any setting.
4. **Approve a source.** The user's action (file dialog, typed URL, CLI argument) adds the path to
   the source records; the supervisor **restarts the engine** with the extended allow list and
   recovers (Restart recovery). Restart cost is measured in the spike; if it is too high, the
   upgrade path is to keep `prepare` outputs as Parquet in the staging directory across restarts.
5. **Approve an export.** No restart: DuckDB writes into the staging directory (already allowed),
   and trusted I/O finalises the file (Restart recovery, exports).

What each layer must block, tested on the pinned versions in gate 6:

| Statement or access | Guard (restricted) | DuckDB (locked config) |
|---|---|---|
| Read an approved source through the node's input | allowed | allowed |
| Read an unapproved file (same directory as an approved one, `/etc/hosts`) | blocked | blocked |
| Read an unapproved URL | blocked | blocked |
| `COPY … TO` a path outside staging | blocked | blocked |
| `COPY … TO` the staging directory | blocked | allowed (trusted I/O uses it) |
| `SET`, `RESET`, `PRAGMA` changing a setting | blocked | blocked (locked) |
| `INSTALL` an extension | blocked | blocked (no network fetch of extensions; external access off) |
| `LOAD` an extension by file path | blocked | blocked (path not allowed) |
| `LOAD` an already-loaded bundled extension | blocked | allowed (no effect) |
| `ATTACH` a database file | blocked | blocked unless the path is approved |

The spike records the actual result of every row on native DuckDB and DuckDB-Wasm, with the guard
on (restricted) and off (unrestricted). A row whose DuckDB column does not hold on the pinned
version is a finding: either the guard is the only protection and this is written in
[security.md](security.md), or the version is changed.

In the browser, layer 2 has less to protect (no disk): DuckDB-Wasm reads registered buffers and
URLs, extensions come only from the app's own origin, and the same allow list applies to URLs.

### Application-level authorisation

DuckDB's settings restrict DuckDB only. terrio, Rust file and network calls, and any other library
in the engine are not covered by them. So:

- Every I/O operation in `geomarmot-engine` (DuckDB registration, terrio reads and writes, HTTP,
  `gs://`, staging) goes through one function, `io::authorize(path_or_url, read|write)`, which
  checks the same approved list and the staging directory. A test lists every call site of
  `std::fs`, `terrio` I/O and HTTP clients in the engine and fails if one bypasses it.
- The engine process receives approvals only from the app process (or the CLI's arguments); a
  graph file never approves anything.
- **No OS sandbox in the first release.** Process separation gives kill-and-restart isolation, not
  file-system isolation. An OS sandbox for the engine process (macOS App Sandbox, Linux Landlock,
  Windows AppContainer) is listed after the first release.

```
                 geomarmot-ai ─┤                              │
   (providers, privacy gate,   │                              │

             ┌──────────────── geomarmot-core ─────────────────┐  geomarmot-cli
             │ graph model · compiler · SQL guard · kit         │◀─ (run a saved
             │ transformers (SQL + kernels) · generations/leases│    graph headless)
             │ Engine trait: in-process │ IPC client │ Wasm bridge│
             └──────────────────────┬───────────────────────────┘

```

- Layering as in RustGIS: no crate below `geomarmot-app` depends on egui, winit or wgpu; CI checks it.
- Only `geomarmot-io` imports terrio, at a pinned version.
- **Generations and leases stay explicit**, as in [architecture.md](architecture.md): a generation
  owns its views, `prepare` tables, source handles and kernel tasks. Retirement stops new leases;
  existing reads retain their resources until the last lease ends. Cancel superseded compile work
  separately. Engine-managed spill files live with their engine/session; never delete them while
  reads still use them. Keep backpressure and stale-result checks from the current compiler.
- **The desktop replaces the Python server's responsibilities.** Specify credential discovery,
  scoped bucket access, token refresh and direct model calls. The static browser build keeps its
  sign-in and direct-provider paths, subject to CORS. Decide the locally served browser/proxy and
  environment-key relay support policy before removing the server; preserve it until then.

## What carries over

- `transformers/*/tests.json` and the fixture builder: the specification, unchanged. The Rust
  runner keeps the comparator's full semantics (column types, geometry dimensions, tolerances,
  ordering, expected errors).
- Transformer SQL, ported from `index.js` to Rust nearly verbatim, since the engine is the same.
- Saved graphs (`geomarmot-graph` v1), including user SQL, its restricted/unrestricted mode, and
  generated transformer templates: same intended dialect, but version differences still require
  compatibility tests. Fixtures do not cover arbitrary saved SQL. Preserve originals, report
  unsupported nodes, and never silently rewrite SQL. Add generated graph round-trips now and a
  representative graph corpus before release.
- Every feature of today's browser app, in the browser build (owner decision).
- The rules in [AGENTS.md](../AGENTS.md) remain authoritative. The recorded desktop-keychain
  decision is a proposed policy change: update that rule with the assistant port before storing
  keys there; this plan alone does not override it. Preserve all existing key-leak protections.

## Spike (three weeks; go, no-go or inconclusive)

The time box is fixed; what does not fit is reported as inconclusive, not extended.

Pin `duckdb` (native) and DuckDB-Wasm to versions with the same DuckDB core where possible,
`terrio`, `geo`, `geos`, `h3o`, `eframe`, `egui-snarl`, `walkers`, Arrow and the Rust toolchain.
Record versions, feature flags, extension hashes and target availability in the report. All
performance comparisons run on the reference Mac, in release builds, with fixed thread counts,
warm-up, repeated runs and median/range. UI work runs on macOS (native) and Chromium (wasm); Linux
and Windows get the runtime check in gate 7; their UI usability moves to Phase 5.

### Budgets and how they are measured

Defaults; the owner may change them. Every budget is measured over **10 runs after one warm-up**,
reporting median and worst, on the reference Mac, release builds, on AC power, with no other
foreground application, the window or tab visible and focused. Today's browser app is measured the
same way where the measure applies, for comparison.

| Budget | Measured from → to | Default |
|---|---|---|
| Desktop start | process launch → first frame of an empty, interactive canvas, with the engine process up and extensions loaded; OS file cache warm (first launch after install recorded separately) | median ≤ 2 s |
| Browser start (warm) | navigation start → first interactive frame with DuckDB booted and extensions loaded; app served from a local static server; HTTP cache warm | median ≤ 2 s |
| Browser start (cold) | as above, cache disabled, no network throttling | median ≤ 5 s |
| Web assets, initial | Brotli-compressed bytes as served, of everything needed for the first interactive frame (app.wasm, JS glue, DuckDB-Wasm, extensions loaded at boot) | ≤ 30 MB |
| Web assets, optional | Brotli-compressed bytes loaded on first use (kernels.wasm, geos-wasm, Excel and Zarr support), counted per feature | recorded; ≤ 15 MB in total |
| UI responsiveness | frame times over the whole run of a kernel workload lasting ≥ 10 s (the overlay fixture repeated, or a generated workload), from egui's frame timing (desktop) and a Chromium performance trace (browser) | p95 ≤ 33 ms, p99 ≤ 50 ms, longest stall ≤ 100 ms |
| Cancellation | the four steps in [Cancellation](#cancellation) | as in that table |
| Source approval (desktop restart) | approve a new source in a graph with 5 sources and a kernel node → graph recompiled and interactive, on fixtures | median ≤ 3 s |

### Gates

1. **Fixtures on native DuckDB from Rust.** The Rust runner passes Bufferer (both per-feature
   projections), Reprojector, Dissolver, AttributeFilter, FeatureJoiner on all three `Engine`
   implementations (in-process, engine process, DuckDB-Wasm). Cross-check comparator results with
   the current harness. Include an H3 and a per-feature geometry-kernel case before accepting their
   bridge and dimension/type contracts.
2. **Overlay kernel.** GEOS (native) and `geo` on the overlay fixtures: same faces within existing
   tolerances, same covering sets, same rejections, valid output. Require existing
   ambiguity/clearance rules; do not accept smaller face counts or misattribution as an explainable
   numerical difference. This gate is correctness only: fixtures are too small to time. If both
   pass, the choice waits for the performance checkpoint (GEOS by default until then); if only
   GEOS passes, the browser's kernel worker uses `geos-wasm`, as today's app does.
3. **Readers.** One format per reader path: terrio vs DuckDB `ST_Read` on the generated
   GeoPackage fixture (time to a DuckDB table), and Parquet over HTTP range reads from a local test
   server (bytes transferred). Check schema, CRS, geometry and attribute types after each read.
   Record bytes copied, peak memory and conversion time; one staged export/read-back check
   (GeoPackage through terrio). The full format inventory is Phase 2.
4. **Cancellation, recovery and responsiveness, both targets.**
   - Desktop: cancel a long scan, a nested-loop join and a stuck kernel in the engine process;
     each meets the cancellation limits, the stuck ones by process kill. Kill the engine during an
     import, a compile, a preview and an export (Restart recovery, tested).
   - Browser: the same cancellation cases, the stuck ones by terminating the DuckDB worker or the
     kernel worker; a stuck preview is killed without disturbing the main graph.
   - Both: results from an old epoch, generation or cancelled request are dropped; UI
     responsiveness, start and source-approval budgets met; peak total memory recorded.
5. **One usable flow.** Open a fixture file, add two transformers, see table and map, export; on
   macOS desktop and in Chromium. Keyboard navigation and text entry work in the canvas and
   inspector. Keep an automated Chromium test in addition to egui simulation.
6. **Security and lifecycle.**
   - Every row of the layer table in [Security](#security), on native DuckDB and DuckDB-Wasm, with
     restricted and unrestricted SQL; results recorded against the expected columns.
   - The `io::authorize` call-site test passes: no file, terrio or HTTP access in the engine
     bypasses it.
   - A retired generation's views, `prepare` tables and kernel tasks are freed once its last lease
     ends, and a superseded compile's partial generation is dropped (checked by counting relations
     and tasks before and after).
7. **Runtime check per target.** In CI on macOS (arm64), Linux (x86_64) and Windows (x86_64),
   with network access disabled for the test step: start the engine, load every bundled
   extension, lock the configuration, run one spatial query (`ST_Area(ST_Transform(…))`) and one
   Parquet read, exit 0. In Chromium: the same against the web build. A build that compiles but
   cannot load its extensions fails this gate.

The report gives evidence per gate and provisional choices for each kernel and reader.
**Go:** all seven gates pass, and no unresolved blocker prevents the intended targets.
**No-go:** a required capability fails with no acceptable bounded remedy.
**Inconclusive:** evidence or agreed budgets are missing when the time box ends; do not treat it as
a pass or start an open-ended rewrite. Report a bounded follow-up and its decision question.
Timings on fixtures compare small workloads only; they do not establish the fastest large-data path.

## Phases after a "go"

The CLI comes before the UI, so native execution can be measured headlessly before the UI is built.
Graphs reference sources rather than embedding data: sources and outputs are bound by command-line
arguments (`--source name=path`, `--output name=path`), which are the CLI's approvals; the CLI uses
the same SQL guard and exit codes report success, failure per node, and cancellation.

| Phase | Content | Done when |
|---|---|---|
| 1. Core | graph model, compiler, `Engine` trait (three impls), engine host, engine process and supervisor, source records, SQL guard, kit, fixture runner, `geomarmot-cli run graph.flow.json` | fixture runner green on the ported transformers |
| 2. I/O | readers and writers for today's formats per the spike's choices, staged exports, remote URLs, `gs://`; inventory every format option in [formats.md](formats.md) (Excel header/date/ID behaviour, Zarr window pricing and codecs, …): a format name alone is not parity | I/O tests ported and green on both targets; every reader checked for schema, CRS, geometry and types; every writer round-trips |
| 3. Performance checkpoint | port the benchmarked transformers first (Reader, AttributeFilter, FeatureJoiner, StatisticsCalculator, Dissolver, AreaOnAreaOverlayer, PolygonToH3, Writer); run the three workloads below through the CLI | the checkpoint criteria below pass; **the UI phase does not start before this** |
| 4. Transformers | the remaining transformers, SQL ones first, then kernels | every `tests.json` green on both engines |
| 5. UI | canvas, inspector, table, map, modals, undo, workspaces, compile loop with cancellation; Linux and Windows desktop; keyboard, clipboard, readable scaling, assistive-technology checks; Firefox/Safari support defined | parity checklist UI rows green on macOS, Linux, Windows and the supported browsers (Playwright for web, `egui_kittest` plus a desktop smoke test per OS) |
| 6. Assistant | providers, privacy gate, tools, preview engine process / workers, generated transformers, keychain | assistant and security rows green |
| 7. Packaging | `cargo-dist` (archives, MSI, installers) plus `cargo-packager` for `.dmg`, `.AppImage`, `.deb`; signing and notarisation; Trunk build for the web | offline installation and launch tested on clean machines; signing/notarisation verified |
| 8. Switch-over | parity sign-off, old graphs open, JavaScript app and Python server archived, AGENTS.md rewritten | migration-specific parity and release gates pass; rollback and deployment policy documented |

### Performance checkpoint (phase 3)

The central assumption — that the native engine is much faster on large data — is tested here,
before the most expensive phase. Three separate workloads, generated by a seeded script at test
time, never committed:

| Workload | Graph | Sizes |
|---|---|---|
| **Relational** | Reader → AttributeFilter → FeatureJoiner → StatisticsCalculator → Writer, on point and attribute tables | 10⁶, 10⁷, 10⁸ rows, and the largest today's browser app completes |
| **Overlay** | Reader ×2 → Dissolver → AreaOnAreaOverlayer → Writer, on polygon layers with realistic vertex counts and overlap | up to today's cap (200,000 features); above it only with the benchmark override |
| **H3** | Reader → PolygonToH3 → Writer | up to today's cap (2,000,000 cells); above it only with the benchmark override |

**Caps stay in production.** `MAX_OVERLAY_FEATURES` and `MAX_MATERIALISED_CELLS` are unchanged.
The CLI accepts `--bench-override-caps` only when built with the `bench` feature, never in shipped
builds; an overridden run also sets a hard limit: DuckDB `memory_limit`, a temp-disk limit, and an
OS limit on the engine process's memory (`setrlimit` on macOS/Linux, a job object on Windows).

**Measured** on the reference Mac: wall time per node and end to end, peak memory of the engine
process, temp disk used, and the cancellation limits on the largest size of each workload.

**Pass when:**

1. **Mandatory:** on every size today's browser app completes, the native run is faster end to end.
2. **Mandatory:** the relational workload completes at least one size today's browser app cannot.
3. **Mandatory:** at a memory limit below the workload's in-memory need, every run either
   completes by spilling within the temp-disk limit, or stops with a clean resource error naming
   the node, and the engine stays usable. A crash or an OS kill fails the checkpoint.
4. **Target, not mandatory:** at least 3× faster than today's browser app on the largest size it
   completes, per workload. Missing it does not stop the project automatically; the owner decides.
5. The GEOS-vs-`geo` and terrio-vs-`ST_Read` choices are made from these numbers.

If a mandatory criterion fails, stop and decide with the owner before building the UI. New values
for the caps are proposed from the overridden runs, never adopted silently. Real datasets and a
corpus of saved graphs, when available, are added to this benchmark; they are release gates (phase
8) before claiming large-data performance or switching users over.

[parity.md](parity.md) gains rows for: privacy-gate downgrade, key leakage, preview isolation, SQL
guard refusals, unrestricted SQL bounded by DuckDB's locked configuration, engine lifecycle,
restart recovery, remote credentials, graph compatibility, accessibility, the static web build,
and the deliberate browser difference (one kernel worker). Preserve the existing comparator
independently of the implementation under test; cross-check a Rust comparator against the current
runner before relying on it.

Offline means an installed app can launch and process local files without network, as in
[ADR 0008](decisions/0008-offline-promise.md). Basemaps are optional network data: disable or gracefully
handle them offline, preserve attribution online, and test a fresh offline profile. A hosted web
app reopening offline remains a separate service-worker decision.

**Estimate:** keeping DuckDB avoids a new SQL dialect, but native extension packaging, the engine
process, the browser bridge, kernels and UI remain unproven. Estimate each phase after the spike,
re-estimate after the checkpoint, with explicit uncertainty and maintenance time for the existing app.

## Risks

| Risk | What we do |
|---|---|
| DuckDB-Wasm and native DuckDB differ in version or functions | Pin both; every fixture runs on both in CI. |
| Bundled native extensions fail to load on a platform (they depend on DuckDB version and platform) | Lock file per platform, as `duckdb-extensions.lock.json` today; gate 7 runs an offline load-and-query test on every target in CI. |
| A DuckDB setting in the layer table does not hold on the pinned version | Recorded in gate 6; the guard is then the only protection for that row and security.md says so, or the version changes. |
| Restarting on every source approval is too slow | Measured against its budget; upgrade path: keep `prepare` outputs as Parquet in staging across restarts. |
| Arrow IPC between app and engine processes costs too much | Only displayed data crosses; measured in gate 4 and at the checkpoint. |
| `geo` overlay differs from GEOS | The spike decides correctness, the checkpoint decides speed; GEOS stays the reference in tests. |
| Browser overlays slower than today (one kernel worker) | Accepted by the owner; recorded in parity.md; measured at the checkpoint. |
| No OS sandbox around the engine process | Application-level `io::authorize` plus DuckDB's locked configuration; OS sandbox listed after the first release. |
| terrio is pre-1.0; code/data license obligations vary by pinned dependency and enabled features | Pin and inspect manifests, notices and CRS-data terms for the shipped feature set; carry required attribution and source obligations. Test fallback availability per target and format. |
| egui UX and accessibility vs today's DOM UI | Early keyboard, clipboard, text and assistive-technology checks on supported targets; AccessKit availability alone is not acceptance. |
| The rewrite stalls | The JavaScript app keeps working until phase 8; each phase ends with passing tests; the checkpoint stops the project before the UI if the speed is not there. |
